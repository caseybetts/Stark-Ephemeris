## Recommended development sequence

### RUN-01 — Establish a trustworthy baseline

**Baseline slice complete (2026-11-02).** Funded purchase, activation, finance reporting, reset, shared-antenna behavior, and per-satellite yield/failure reporting have been reviewed. The then-current 20% rule was measured in two same-seed single-spacecraft runs and one funded two-spacecraft run. The repeated single-satellite revenue and costs matched, while the manual stopping times and attempt counts differed; do not claim exact operational replay from these samples. These revenue figures are historical under the updated 30% rule. Include the existing map/readout review only where it affects understanding of these actions.

The recorded sample set covers two repeated single-spacecraft runs and one funded two-spacecraft case, with setup, seed, duration, policy, revenue, costs, capital, remaining imagery, outcomes, and approximate wall time. It does not isolate hardware/orbit effects; use comparable independent runs for those questions. No balance values were changed as part of the measurement.

**Finding:** These samples provide a first observed revenue/cost range for RUN-02, but they do not establish a balanced economy or a guaranteed attainable objective. Do not silently rebalance the existing prototype or declare profitability from potential imagery value. Exact deadline enforcement belongs to RUN-03.

### RUN-02 — Define the first mission

**Status: Core M01 rules agreed 2026-11-03; numeric inputs remain provisional and the mission is not implemented.** The first mission reuses the current market, weather, spacecraft, and finance systems. It tests satellite setup and ground-side policy in one short attempt, without adding dynamic events or a campaign economy. Per the agent guidance, implementation agents should verify the mission framework and technical edge cases; the human leads player-experience playtesting, and broad balance tuning waits for that feedback.

#### RUN-02 decisions recorded

**Provisional implementation inputs:** $55.12M allowance, $5,000 per-station setup fee, $2,000 delivered-revenue target, 24-hour duration, and 300× default. #### M01 implementation handoff (RUN-03)

- Setup is a draft state: show the $55.12M allowance, four $5,000 station setup charges, one chosen spacecraft package, editable orbit, initial ground priorities, and the resulting remaining setup cash before the player starts time. Reject an invalid or over-budget setup without changing the clock or finance ledger.
- Calculate and display the selected orbit's aggregate access minutes per day through the four active stations. Explain that simultaneous access windows can compete for a station antenna. This readout is a planning estimate, not guaranteed collection/downlink throughput.
- On mission start, initialize a clean attempt with the approved budget, one purchased satellite, the fixed station network, scenario market/weather state, and run-scoped performance history. Post each station setup charge once for that attempt, separate from daily upkeep and spacecraft capital spending. Retrying creates a fresh attempt and charges setup again from the reset budget.
- During the run, category-priority edits remain ground-side until the next valid contact upload. Pause and playback controls do not alter simulation outcomes. No station/spacecraft purchases or orbital maneuvers occur after start in M01.
- At exactly 24 simulation hours, process each event with a completion timestamp at or before the deadline once, then stop advancement. A settlement completed at the deadline counts; a partial transfer does not. Any unfinished image or operation appears in the debrief without being credited as revenue.
- Evaluate only ledgered downlink revenue against the proposed $2,000 target. Show the target and outcome, delivered revenue, setup fees, daily operating costs, spacecraft capital, ending cash, per-satellite yield, and onboard/deleted imagery as separate values. Never add starting cash, unused budget, or potential image value to earned revenue.
- Retry restores the same mission market, weather seed, initial budget, station network, fleet baseline, and empty operational history while allowing a new package/orbit and new priority policy. It must not reuse any prior attempt's ledger entries, images, commands, or capture statistics.

#### Domain boundary

- Add an immutable M01 definition containing the proposed $55.12M allowance, four starter stations, provisional setup charge, default market/weather seed, 24-hour deadline, delivered-revenue target, and available spacecraft package choices. Keep player selections in a separate setup draft.
- Add a renderer-independent run controller with `setup`, `running`, `paused`, and `completed` states. It validates and starts a draft, allows pause/resume, caps requested advancement at the deadline, and evaluates completion idempotently. No UI or Cesium types belong in this module.
- Start/retry through an attempt boundary. It may construct fresh `CompanyFinance`, runtime, operational loop, station network, cell market, performance history, and image/command IDs, or reuse these services only when their reset path demonstrably clears every prior attempt's mutable state. In either case, apply the selected package/orbit, fixed scenario, and same seed; no prior ledger entry, image, command, or capture record may survive.
- Validate orbit fields, package choice, and total setup affordability before mutating a finance ledger or starting the clock. On acceptance, construct the selected single spacecraft and record its purchase plus the four station setup charges at simulation time zero. Show setup charges, capital purchase, and later operating costs separately; only downlink revenue determines victory. Setup fee amount and accounting category remain provisional inputs.
- Route animation playback and any explicit simulation advance through the run controller. Split a large advance at the exact deadline, let the operational loop process events at that endpoint once, then complete the run and reject further advances. A full settlement completed at the deadline counts; partial bytes do not.
- Keep the market/player-priority system's existing defaults for initial priorities. During the run, player changes remain ground-side until normal contact upload. No fleet/station purchases or maneuvers are available after launch.
- Build the debrief from domain snapshots: target and result, elapsed time, delivered revenue, setup costs, capital spending, operating costs, ending cash, per-satellite yield/failures, and onboard/partially transferred/deleted imagery. Explain only observed bottlenecks; do not estimate hypothetical lost revenue or recommend an untested alternative.
- Retry returns to setup with the same market/weather seed and budget. It may retain the last setup draft for editing, but starts with clean operational and finance state. No cross-level carryover is required.

#### App integration sequence

1. Keep attempt state behind one setup/retry boundary. Prefer a fresh attempt context if it simplifies state ownership; otherwise centralize and verify the complete reset contract. Rebuild spacecraft/station views and map layers after applying the new setup.
2. Add a setup surface that edits equipment and orbit, previews remaining budget, and gates Start on valid/affordable configuration. Show the provisional mission brief and exact deadline before start.
3. Add lifecycle controls and route clock changes through the controller. Disable simulation-only operations after completion; keep pause and speed controls available only while running.
4. Add a debrief surface and Retry action. Derive all totals from `CompanyFinance`, `CellMarketState`, and `SatellitePerformance`; clear prior state only by constructing a new attempt.
5. Keep the existing continuous prototype available only if it can be preserved without maintaining two competing initialization paths; otherwise make M01 the default entry flow and retain development fixtures behind their current query flag.

**Acceptance handoff:** Invalid/unaffordable setup leaves time and finance untouched; valid setup posts each start transaction once; identical inputs/actions replay consistently; pause and all playback rates obey the deadline; a large step cannot create post-deadline income; an event ending exactly at the cutoff is applied once; repeated finish/evaluation cannot duplicate results; partial transfers are not credited; retry clears all attempt state while preserving seed; and the result is understandable in the browser. Agents verify technical behavior and boundary cases; the human evaluates pacing and balance.

A future multi-spacecraft mission remains planned as a separate fleet challenge, after setup and evaluation rules are designed.
